# 10 设计特点与取舍

## 学习目标

能从代码证据解释项目采用的实现方式及其成本；区分“代码可观察到的特点”与“开发者原始设计意图”。

> 下表中若无明确源码注释证明动机，均按“从当前实现观察到的设计特点”描述，不将合理推测包装成开发时的原始决策。

| 设计选择 / 观察到的特点 | 解决的问题 | 当前实现 | 优点 | 缺点 | 其他可选方案 | 本项目采用的合理解释 |
|---|---|---|---|---|---|---|
| C99 | 以低层语言明确控制字节与内存布局 | 根 CMake 强制 C99；固定宽度整数来自 `<stdint.h>` | 易展示协议字节处理和嵌入式常见模式 | 手动管理内存与边界；缺少语言级安全抽象 | C++、Rust，或生成式协议编码 | 这是仓库明确的技术约束；适合展示 C 编解码基础，不代表车载量产项目必须使用 C99。 |
| Protocol Core 与 Winsock Transport 分离 | 避免协议解析依赖 socket API | Gateway 接受完整报文；TCP Server 做收发/分帧；CMake 仅 Windows 加网络代码 | 核心测试可脱离网络；Transport 职责集中 | 核心 API 不能增量消费流；Transport 仍有平台耦合 | Transport interface、跨平台 socket adapter、事件循环 | 分层使演示便于单测；完整跨平台仍需额外抽象。 |
| 按字段序列化 | 消除结构体 padding、对齐与主机字节序差异 | `doip_header.c` 与 Body Codec 用移位、掩码逐字节读写 | Wire 格式显式、易审查 | 字段较多时样板代码增加 | 通用 serializer / 代码生成 | 目前格式固定且较小，显式实现直观。 |
| 不用 C Bit-fields 表示线上字段 | 避免位域布局依赖编译器和 ABI | `doip_header_t` 只保存语义字段，Codec 负责转成 8 字节 | 内存布局与协议布局分离 | 需手工移位；复杂位域校验更冗长 | 手工掩码或生成器 | 当前 Header 无需位域也能表达，普通整数清晰且稳定。 |
| Buffer + Capacity 显式参数 | 调用者可声明可写范围 | 各 Encoder 接收 `buffer_size`/`output_capacity`，写前校验 | 便于静态数组和边界单测；避免盲目写入 | API 参数多；不能验证指针实际分配对象大小 | `span` 类抽象、拥有型 Buffer、动态容器 | 与 C99 无内建切片类型相适配，但仍需调用者传真实容量。 |
| 区分 Header、Payload Body、完整 Message | 各层只校验自己负责的数据 | 独立 Header、Request/Response Body、Message API | 可复用、错误范围清楚、业务解码前验证 framing | 某些消息会出现分层解析的重复 Header 读取 | 单一端到端解析器、流式 Parser 对象 | 当前抽象适合模块测试；Server 先读 Header 是 TCP 分帧所需，Gateway 再通过 Message API 做完整输入校验。 |
| `doip_message_view_t` 借用 Payload | 避免消息解码额外复制 Payload | `payload = buffer + 8`，记录 Header 值 | 无分配、无 Body 冗余拷贝 | 生命周期依赖输入 buffer，调用方需理解借用语义 | 拥有型消息对象、拷贝式解码 | 固定缓冲区流程中输入仍存活到请求解码完成；需要异步留存时需改为拥有型数据。 |
| TCP 精确读/写循环 | TCP 的 `send`/`recv` 不保证一次完成 | Server/Tester 累计正数返回字节，重试 would-block/interrupted | 可处理短读/短写和非阻塞 I/O | 状态机和错误分支增加；Server 无帧级 deadline | 阻塞精确 I/O、IOCP/异步框架、增量 Parser | 当前循环清楚体现 TCP 字节流；生产实现还需更完整的超时与取消策略。 |
| 单客户端同步服务 | 简化连接和状态所有权 | `doip_tcp_server_run` 接受一个客户端后处理到结束再 accept | 逻辑直观，Gateway 仅一个状态对象 | 慢客户端阻塞其它客户端；无并发吞吐 | 线程池、select/poll/IOCP 多连接模型 | 适合最小演示，但不能外推为可扩展服务端设计。 |
| 固定 4096 字节本地 Payload 上限 | 避免动态分配并控制栈缓冲空间 | Server 和 Tester 都使用固定本地限值；Server 数组为 8+4096 字节 | 简单、易审计、拒绝超大声明长度 | 资源/功能固定；不代表标准最大值 | 配置上限、分块/动态缓冲、上限协商 | 代码和 README 明确将其定义为本地安全策略，非协议标准边界。 |
| 错误枚举返回 | 不依赖异常机制或全局错误变量 | `doip_result_t` 统一 API 状态；socket 错误另记录 | C 风格显式分支，可测 | `UNSUPPORTED` 过宽；上下文细节需要日志辅助 | 错误结构体、模块专属错误码、HRESULT 风格 | 对小型 C API 易用，但扩展产品需更精确错误诊断。 |
| Gateway 在状态更新前检查输出容量 | 避免无法输出响应却先提交激活状态 | 先解码/校验、检查 17 字节，再调 State Process | 容量失败无业务状态副作用；测试明确验证 | 增加固定响应尺寸耦合 | 先构造响应暂存，再提交事务状态 | 当前响应固定 17 字节，前置容量检查简单有效。 |
| 状态按逻辑地址而非 socket 关联 | 当前规则以 Tester Logical Address 区分请求 | State 保存单个 `client_logical_address`；连接结束时 Server reset | 展示逻辑地址驱动的最简状态路径 | 无法表达多连接、多路由或地址绑定策略 | 每连接上下文、地址到 ECU 路由表 | 适合演示，但不能替代真实 Gateway 会话管理。 |

## 设计层面的优先级

当前实现把可读性、固定边界和单模块测试放在较高位置；它没有试图解决高并发、标准完备性、诊断 ECU 接入或生产级监控问题。面试回答时可先指出代码事实，再说明该方案适用于教学演示的条件，最后给出扩展成本，不要声称性能或安全验证已经完成。

## 面试时需要能够讲清楚的问题

- 如何证明 C struct 内存不能直接当作 DoIP Header？
- 显式 Capacity 解决了什么、又无法解决什么？
- `doip_message_view_t` 如何减少拷贝，带来什么生命周期风险？
- 为什么单客户端模型不能直接简单扩成多客户端？
- 4096 字节代表什么，不代表什么？
- 哪些取舍有源码注释明确支持，哪些只是基于当前实现的合理解释？

## 本章需要掌握的知识点

- 先说实现证据，再说收益与代价；不要把推测说成原始设计动机。
- 固定缓冲区、显式长度和逐字段序列化有利审查，但不是完整内存安全证明。
- 单客户端和 4096 限制是当前实现边界，不是 DoIP 标准特性。
- 扩展并发或流式解析会同时影响状态模型、Transport、错误处理和测试。
